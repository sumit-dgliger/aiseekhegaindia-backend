1. Executive recommendation

Framework Migrate the Express stub to Fastify + TypeScript. Layered plugins/modules; do not use NestJS.
OAuth flow Backend-mediated Authorization Code (redirect to Google → callback on API). Scopes: openid email profile.
Session Signed JWT in httpOnly Secure cookie (SameSite=Lax). No Passport. No opaque server sessions table for v1.
Database Neon (serverless Postgres) via Prisma. Same Neon project for local + prod (use separate branches/DBs); no Docker Postgres, no Cloud SQL.
GCP host Cloud Run (containerized Node API). Secrets from Secret Manager in prod; .env locally. GCP used for OAuth client + hosting, not for the database.
Auth provider Custom Google OAuth with existing client credentials. Do not adopt Firebase Auth / Identity Platform for v1.
Front contract Next.js: “Sign in” → GET /api/v1/auth/google. After login, call GET /api/v1/auth/me with credentials: 'include'.

4. Framework & project structure

Decision

Replace the Express stub with Fastify + TypeScript. Remove Express packages (express, cors, helmet, morgan and their @types/*). Use official Fastify plugins.

Target tree

src/ index.ts # build app + listen app.ts # fastify factory: plugins + routes config/ env.ts # zod-validated env db/ prisma.ts # PrismaClient singleton modules/ auth/ auth.routes.ts # FastifyPluginAsync auth.controller.ts auth.service.ts google.ts # OAuth URL, token exchange helpers session.ts # sign/verify JWT, cookie helpers users/ users.service.ts plugins/ requireAuth.ts # preHandler / decorate request.user errorHandler.ts types/ fastify.d.ts # FastifyRequest user augmentation prisma/ schema.prisma migrations/ Dockerfile

Libraries

  • fastify — HTTP framework (replace Express)
  • @fastify/cors — CORS with credentials
  • @fastify/helmet — security headers
  • @fastify/cookie — read/set cookies
  • @fastify/rate-limit — auth route limits
  • zod — env validation
  • dotenv — load .env in local/dev
  • @prisma/client + prisma (dev)
  • google-auth-library — OAuth2 client / token verify
  • jsonwebtoken + @types/jsonwebtoken — session JWT

API versioning

All new routes under /api/v1. Keep existing /health unversioned. Update /api/v1/meta features.auth to true when Phase 4 ships. Re-implement current stub routes on Fastify with the same paths/responses.

5. Auth design

Why not the alternatives

OptionVerdictReason
Backend Authorization Code + PKCE Chosen Secret stays server-side; works with httpOnly cookie session
Front PKCE-only (public client) Rejected We already have a confidential client secret; backend exchange is simpler to secure
GIS ID token → POST /auth/google Rejected for v1 Fine alternative later; redirect flow needs fewer front Google SDK choices
Passport Google strategy Rejected Extra abstraction; manual Fastify routes are clearer for one provider
Opaque session in Redis/DB Deferred JWT cookie enough for v1; revoke-by-logout only

Endpoints

MethodPathAuthBehavior
GET /api/v1/auth/google Public Create state + PKCE; store verifier in short-lived httpOnly cookie oauth_pkce; redirect to Google
GET /api/v1/auth/google/callback Public Validate state; exchange code; upsert user; set asid; clear PKCE cookie; redirect to front
GET /api/v1/auth/me Required Return current user from JWT + DB; 401 if missing/invalid
POST /api/v1/auth/logout Optional cookie Clear asid cookie; 204

User fields persisted

Unchanged from prior plan.

  • id — UUID (PK)
  • googleSub — unique string from Google sub
  • email — unique
  • emailVerified — boolean from Google
  • name — nullable string
  • pictureUrl — nullable string
  • createdAt / updatedAt

Front wiring (high-level only)

  • Sign-in button: full navigation to {API_URL}/api/v1/auth/google (not fetch — needs redirect).
  • After return to /auth/callback, call fetch(`${API_URL}/api/v1/auth/me`, { credentials: 'include' }).
  • Logout: POST .../auth/logout with credentials, then clear local UI state.
  • Front env: NEXT_PUBLIC_API_URL=http://localhost:4000 (prod API URL later).

Google Cloud Console (human checklist)

GCP OAuth / Identity setup is unchanged and fine as planned.

  • OAuth client type: Web application (already)
  • Authorized JavaScript origins: http://localhost:3000, https://aiseekhegaindia.com
  • Authorized redirect URIs: add both callback URLs from Decision register
  • Scopes used in code: openid, email, profile
  • APIs: ensure OAuth consent screen is configured (External or Internal as appropriate)
  • Do not enable Cloud SQL Admin API — database is Neon, not Cloud SQL

6. Database & data layer

Comparison

OptionVerdictNotes
Neon (serverless Postgres) Chosen Managed Postgres, branching, pooling, generous free tier; Prisma-native
Cloud SQL PostgreSQL Rejected Higher always-on cost; extra GCP wiring for solo builder
Firestore Rejected Weaker relational joins for curriculum progress; different query model

Decision

Use Neon for both local development and production. Prefer a Neon development branch for local and a production branch for Cloud Run. No docker-compose database.

Prisma schema sketch

User schema unchanged.

datasource db { provider = "postgresql" url = env("DATABASE_URL") directUrl = env("DIRECT_URL") } model User { id String @id @default(uuid()) googleSub String @unique email String @unique emailVerified Boolean @default(false) name String? pictureUrl String? createdAt DateTime @default(now()) updatedAt DateTime @updatedAt } // Progress intentionally NOT in auth milestone

Migrations

  • Local/dev: npx prisma migrate dev against Neon DIRECT_URL
  • Prod: npx prisma migrate deploy in CI / one-off job against prod DIRECT_URL
  • Decision: run migrations as a CI step or Cloud Run Job before new revision traffic — not on every container boot

Local vs production

  • Local: Neon console → copy pooled + direct URLs into .env (dev branch)
  • Prod: Neon production branch URLs in Secret Manager; Cloud Run uses pooled DATABASE_URL
  • Always use SSL (?sslmode=require is typical on Neon connection strings)

Firebase Auth / Identity Platform would offload sessions and multi-provider support, but duplicates the OAuth client you already configured and couples the front to Firebase SDKs. Stick to custom Google OAuth on Fastify for v1. Revisit only if you add multiple IdPs or need managed MFA.

8. Security checklist

  • .env in .gitignore; never commit secrets; rotate GOOGLE_CLIENT_SECRET if it was ever pasted into chat
  • Cookie asid: httpOnly, secure in production, sameSite: 'lax', path: '/' via @fastify/cookie
  • CORS allowlist only with credentials; never reflect arbitrary Origin
  • Validate OAuth state; use PKCE S256; single-use code exchange
  • Verify ID token aud === GOOGLE_CLIENT_ID when using ID token claims
  • Rate-limit auth routes with @fastify/rate-limit; use @fastify/helmet
  • Zod-validate env; generic 500 bodies ({ error: "internal_error" }); log details server-side only
  • SESSION_SECRET ≥ 32 random bytes; different per environment
  • Do not put JWT in localStorage
  • Keep Neon URLs out of git; use pooled URL in the running API

9. Implementation phases

Phase 1

Fastify bootstrap + env validation

Replace Express with Fastify app factory. Add dotenv, src/config/env.ts (zod). Register @fastify/cors, @fastify/helmet, @fastify/cookie. Port /health and /api/v1/meta.

Accept: Server refuses to start with a clear error if required env is missing; /health works on Fastify when env is valid.

Phase 2

Neon + User model

Add Prisma with DATABASE_URL + DIRECT_URL for Neon. Migrate User model; users.service upsert-by-googleSub.

Accept: prisma migrate dev applies against Neon; can create/read a user via service call.

Phase 3

Google OAuth endpoints + session

Implement start + callback + logout as Fastify routes; JWT cookie helpers; PKCE + state; @fastify/rate-limit.

Accept: Browser completes Google login locally; asid cookie set; bad state returns 400; logout clears cookie.

Phase 4

Protected /api/v1/auth/me

requireAuth preHandler; return safe user DTO; update /api/v1/meta features.auth: true.

Accept: With cookie → 200 user JSON; without → 401; meta flag true.

Phase 5

Wire Next.js front (thin)

Sign-in link, optional /auth/callback page, client helper for /me + logout. No redesign.

Accept: From front on localhost:3000, user can sign in and see name/email from API.

Phase 6

Deploy to Cloud Run

Dockerfile, Artifact Registry, Secret Manager (incl. Neon URLs), domain/redirect URI updates. Document Neon + GCP ops in README.

Accept: Production callback URI works; /health and /me succeed on custom or run.app URL.

Deferred (do not implement in auth plan)

Curriculum progress sync API, search, NestJS, Firebase Auth, Redis session store, refresh-token rotation, multi-provider login, email/password, Cloud SQL.

11. Risks & open decisions

Open decisions for the human: none that block coding. Remaining items are ops timing only.

RiskMitigation
OAuth redirect URI mismatch Document exact URIs; fail callback with clear log if Google returns redirect_uri_mismatch
Cross-site cookie on different API domain Use SameSite=Lax + top-level OAuth redirect; credentialed CORS; reverse-proxy under same site later if needed
JWT cannot be revoked server-side Accept for v1; short TTL optional later; logout clears cookie only
Neon cold start / compute limits Use pooled URL; consider Neon scale settings; separate prod branch
Prisma migrate vs pooler Always migrate with DIRECT_URL; never run migrate through the pooler endpoint
Secret leaked in chat/history Rotate Google client secret in Console before prod
